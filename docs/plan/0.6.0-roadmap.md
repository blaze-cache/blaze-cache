# Blaze Cache — 0.6.0 Roadmap (Framework Bindings)

**Date:** 2026-11-23
**Target release:** `0.6.0`
**Baseline:** `0.5.0-rc.1` (query API, IDB schema v2 and devtools are fixed dependencies;
tiered mode is a **flagged sub-scope** — see [`0.5.0-roadmap.md`](0.5.0-roadmap.md))
**Scope:** `@blaze-cache/integration-core` (+ its `/snapshot` server-safe and `/testing`
conformance subpaths), direct bindings for React, Next.js, Vue/Pinia, Svelte/SvelteKit and
SolidJS, examples, SSR/browser tests, release tooling, documentation
**Status:** planned

---

## Go/no-go checkpoint — before beta.1 starts

Confirm what 0.5.0 actually shipped at `0.5.0-rc.1`: devtools (`beta.3`), query API and IDB
schema v2 (`beta.2`) are **mandatory**. Integration-core may start no earlier than
`0.5.0-beta.4` (core frozen), and **`0.6.0-beta.1` must not ship before `0.5.0-rc.1`**,
because the query API is only guaranteed stable at `rc.1`. If tiered mode was dropped at
`0.5.0-beta.4`, it goes to 0.5.x/0.7.0 — **never into 0.6.0**. **0.6.0 does not wait for a
0.5.x tiered release**: it ships without the flagged sub-scope, and the tiered pieces are
added back additively in a 0.6.x once tiered lands. This is a gate, not a risk note.

## Flagged tiered sub-scope (drops cleanly if 0.5.0 beta.4 fails)

Everything below depends on tiered mode being part of the 0.5.0 baseline. If the go/no-go
checkpoint finds it absent, these items are removed from 0.6.0 in one edit — they are not
absorbed as new core work:

- `useBlazeAsyncValue` and the React Suspense/`use()` path (Stage 1).
- The `createResource`/`getAsync()`/`queryAsync()` paths in Solid (Stage 5) and the
  Vue/Svelte async equivalents.
- The `BlazeAsyncState` **eviction rule** and its conformance case — the shared state shape
  itself still ships, since it is useful with any async source (Foundation, rc.1).
- The "Persistence tiers" row of the rc.1 matrix.
- The corresponding items in Goals, Guardrails, DoD and Sequencing priorities.

None of this blocks 0.6.0: the dropped pieces return as an additive 0.6.x when tiered ships.

## Baseline contract — exactly what 0.6.0 consumes from 0.5.0

This is the frozen surface 0.6.0 builds against. Anything not listed here must not be
assumed by a binding. All of it is settled in 0.5.0 beta.1–beta.3, before 0.5.0-rc.1.

| 0.5.0 surface                                                           | Contract 0.6.0 relies on                                                                                                                                                                                     |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createCache({ indexes: true })`                                        | Opt-in indexes; without them `query()` throws a clear setup error (no implicit `fullScan`)                                                                                                                   |
| `query({ prefix, tags, ttlRange, keys, limit, cursor, includeValues })` | `ttlRange` is the expiry filter; `keys` is the value allow-list; `limit` required; `includeValues: true` returns live values and requires `maxEntries`/`maxValueBytes`; unknown cursor key survives deletion |
| `queryAsync()` / `getAsync()`                                           | Tiered-only async counterparts; `query()`/`get()` never silently become async; sync query over a bounded working set warns about partial results                                                             |
| `scan(filter, { cursor, limit })`                                       | Optional `CachePersistence` method returning **metadata only**; with values requested, loads them lazily per page                                                                                            |
| `@blaze-cache/core/shared`                                              | wasm-free, server-safe subpath: redaction patterns, frozen duck-typed `BlazeRecord` guard, `<binding>:<feature>` kind convention, `apply`/summarize helpers                                                  |
| Events                                                                  | Wildcard `on()` + 10 types; `invalidate` carries `keys` **and** `tags`; keyless `remote-invalidate` means broad revalidate                                                                                   |
| Drop log                                                                | A wildcard listener enables it; last detach restores prior state; devtools + binding coexistence is a tested contract                                                                                        |
| Snapshot                                                                | Versioned JSON; unknown version degrades to "no snapshot"; deny-unless-allow-listed redaction from `core/shared`                                                                                             |
| Harness                                                                 | Every example in Chromium; SSR/hydration-parity subset in Chromium/Firefox/WebKit; `bench:ci` baseline with devtools detached                                                                                |

## Goals and non-goals

**Goals**

- Use Blaze Cache directly from each framework's native primitives — context/provider,
  composables, stores, signals — without hand-rolling subscriptions in application code.
- Preserve the **by-reference value contract** in every binding: no deep cloning or deep
  proxying of cached values on the read path.
- Make server rendering safe: no wasm initialisation or IndexedDB access during SSR, **no
  cross-request state leakage**, and a versioned snapshot bridge with no hydration mismatch.
- Share one record envelope, key encoding, tag hierarchy and snapshot format across all
  bindings, enforced by one conformance suite rather than per-framework copies of a test.
- Expose 0.5.0's paged `query()` and — if the 0.5.0 baseline includes it — tiered mode's
  `getAsync()` through **one cross-framework async state shape** (the tiered half is the
  flagged sub-scope).
- Keep `@blaze-cache/react-query` and `@blaze-cache/swr` authoritative for those libraries;
  the new bindings are for apps using Blaze Cache directly.

**Non-goals (explicitly out of scope for 0.6.0)**

- Nuxt, SolidStart, Astro, Angular, Qwik and other frameworks — 0.7.0 candidates. The Solid
  binding is **client-only** (see Stage 5).
- Replacing framework server caches (Next App Router/Route cache, SvelteKit server `load`
  cache) or TanStack Query/SWR.
- Running the core on the server. `@blaze-cache/core` remains ESM/browser-only; server code
  only ever produces serializable snapshots.
- Refactoring the existing `react-query`/`swr` packages onto the new shared core (possible
  0.7.0 follow-up once parity is proven).
- New core engine features — query and devtools are shipped 0.5.0 dependencies; tiered
  storage is never absorbed here (it goes to 0.5.x/0.7.0 if dropped).
- Multi-GB streaming hydration and compaction — 0.7.0 (moved out of 0.5.0's plan).

## Foundation: `@blaze-cache/integration-core`

A framework-free package that every binding builds on. It has two subpaths with different
dependency profiles:

- `@blaze-cache/integration-core` — runtime, depends on `@blaze-cache/core`, browser-only.
- `@blaze-cache/integration-core/snapshot` — **server-safe**: no runtime import of
  `@blaze-cache/core`'s root or `/wasm` entry. It may import `@blaze-cache/core/shared`
  (wasm-free). The build check forbids the core **root and wasm entry**, not every core
  subpath.

1. **Key encoding:** `resolveKey(parts)` — stable, NUL-safe, namespaced keys (e.g.
   `react:user:42`), reusing the conventions in `packages/core/src/utils.ts`.
2. **Record envelope:** the shape is **frozen in `@blaze-cache/core/shared`** in 0.5.0 beta.1:
   `BlazeRecord<V> = { kind: string; v: number; data: V; storedAt: number }`, with a
   duck-typed, version-tolerant `isBlazeRecord` guard. `kind` follows `<binding>:<feature>`
   (e.g. `next:route`); the framework prefix is derivable from it even though the separate
   `framework` tag also exists. Bindings import the guard rather than redefining it, so
   devtools recognition and binding writes can never drift.
3. **Tag hierarchy:** `framework` (shared) → per-binding tag (`react`, `next`, `vue`, `pinia`,
   `svelte`, `solid`) → feature tag (`next:route`, `pinia:<store>`). `purgeKind(cache, kind)`
   and `purgeFramework(cache)` use `invalidateTags` at the right level; a feature tag never
   escapes its parent binding. This resolves the `next:route` vs `next` inconsistency up front.
4. **Stamp helpers:** per-binding `ttlMs`/`tags` defaults and call-site overrides.
5. **Subscription multiplexer — one per cache, not per provider.** 0.5.0 exposes no reactive
   API: there is only wildcard `on(listener)` with 10 event types, and every wildcard
   listener switches on the Rust drop log. `integration-core` therefore owns a single
   refcounted multiplexer in a `WeakMap` keyed by cache instance, shared by any number of
   providers; `subscribeValue`/`subscribeTag`/`subscribeQuery` are views over it with
   throttling, stable snapshot identity and error isolation (a throwing listener never breaks
   its peers). The last unsubscribe removes the wildcard listener and restores the exact
   prior drop-log state. **Tag fan-out cannot rely on event payloads alone**: 0.5.0's
   `invalidate` event carries keys but no tag names, and `remote-invalidate` carries neither;
   the multiplexer keeps a per-watched-tag key mirror hydrated from `keysWithTag()` and
   reconciles it on removal events (the technique core's `CacheSubscriptions` uses). 0.5.0
   adds `tags` to `invalidate` so fan-out no longer has to guess; a keyless
   `remote-invalidate`, or any unknown event, triggers a **broad revalidate** of every
   subscriber. A conformance case attaches devtools and a binding to the same cache, then
   detaches one and asserts the drop log is still correct.
6. **Async state:** one exported shape that every binding maps onto its native async
   primitive (`use()`, `createResource`, Svelte awaited stores, Vue async composables):

   ```ts
   interface BlazeAsyncState<V> {
     status: 'pending' | 'ready' | 'error';
     value?: V;
     error?: unknown;
     stale?: boolean;
   }
   ```

   Semantics must not drift per framework. **Eviction vs invalidation (flagged tiered sub-scope):** an `evict` event
   means the value still exists on disk — keep the last value, set `stale: true`, optionally
   re-fetch via `getAsync()`; `invalidate`/`delete`/`remote-delete`/`expire` mean the data is
   gone and must clear the value. A conformance case drives each event type through the
   adapter.

7. **Snapshot bridge (two modules).** The server has **no cache**: an App Router server
   component passes plain records to `makeSnapshotFromRecords(records, options)` from
   `@blaze-cache/integration-core/snapshot`. On the client,
   `restoreSnapshot(cache, snapshot)` writes into the cache; `makeSnapshot(cache)` is only
   for client-side capture. **Safe serialization:** escape `</script>`, `<!--`, U+2028 and
   U+2029 after `JSON.stringify`; embed as `application/json`, never inline JS.
   **Redaction** is deny-unless-allow-listed using the patterns from
   `@blaze-cache/core/shared` (importable by the server-safe subpath) — integration-core
   never imports `@blaze-cache/devtools` or core's root/wasm entry.
   **Value reads use 0.5.0's `keys` allow-list option**:
   `query({ keys: allowList, includeValues: true, limit, maxEntries, maxValueBytes })`;
   adapters without allow-list support fall back to a bounded key read plus `peek()` of the
   allowed keys. Values are live by-reference objects, never summarized.
   **Restores are not writes:** use the internal, non-persisting, non-broadcasting path —
   insert-if-absent, or compare `storedAt`/HLC so newer IndexedDB data wins. Never
   `persistence.save`, never a multi-tab publish. Unknown schema versions degrade to "no
   snapshot". No module-level cache or singleton: records are passed explicitly per request.
8. **Dual-instance guard:** `integration-core` is a **peerDependency** of every binding (so a
   bundler dedupes it) _and_ registers `Symbol.for('blaze-cache.integration-core')` with its
   version at module init. A second, differing version throws immediately with an actionable
   message instead of silently diverging kind guards and listener registries. CI fails on
   duplicate resolution (`pnpm ls @blaze-cache/integration-core --depth Infinity` must show
   one copy in each binding's graph).

### Conformance harness — `@blaze-cache/integration-core/testing`

Shipped **with** the core in beta.1, not retrofitted. A framework-agnostic suite that takes
a small adapter:

```ts
interface ConformanceAdapter<V = unknown> {
  mount(initial?: V): Promise<{
    read(): V | undefined;
    mutate(next: V): void;
    emit?(event: CacheEvent): void;
    unmount(): void;
  }>;
}
```

`runConformanceSuite(adapter, options)` runs: **identity** (read returns the same reference
after an unrelated mutation), **zero listeners after unmount**, **throttling** (N rapid
mutations produce at most one recompute in the window), **purge scope** (`purgeKind` leaves
other kinds' records intact), **error isolation** (a throwing listener does not break peers),
**snapshot version skew** (unknown version → no snapshot), and **async state** (pending →
ready/error shape), **evict-vs-invalidate transitions** (via `emit`), **devtools coexistence**
(attach devtools + binding, detach either, assert drop-log state) and **multiplexer refcounting**
(two mounts on one cache share one wildcard listener). Each binding supplies a ~50-line
adapter; rc.1's Identity and Teardown gates call the same suite, making them mechanical rather
than bespoke. React/Vue/Svelte/Solid adapters mount under a DOM environment (`happy-dom` or
equivalent in `node:test`) — plain `node:test` cannot mount these frameworks.

**Acceptance criteria:** core and `/testing` unit-tested (key collisions, envelope guards,
tag hierarchy, serialization escaping, redaction allow-list, concurrent-request isolation,
dual-instance throw, duplicate-resolution CI check); no framework dependency in the package
graph; `@blaze-cache/core` tests unchanged.

## Stage 1 (0.6.0-beta.1) — React bindings

Create `@blaze-cache/react` following existing package conventions (plain `tsc`, `src/*.ts` +
barrel, `test/*.test.mjs` with `node:test` under `happy-dom`, package README with the standard
logo header, `sideEffects: false`, peer deps on React 18/19 **and**
`@blaze-cache/integration-core`).

1. **Provider:** `<BlazeProvider cache={cache}>` (or `{ createCache }` options) supplies the
   cache via context; accepts `onError`; never initialises wasm at module scope.
2. **Value hook:** `useBlazeValue<V>(key, options?)` built on `useSyncExternalStore` over
   `subscribeValue`. **Pass an explicit `getServerSnapshot`** that reads the value from the
   provider's restored snapshot — never the live cache — and returns a stable reference
   identical to the client's first pass. This is what prevents the hydration warnings the
   snapshot bridge exists to avoid. Add `useBlazePeek` for side-effect-free first render.
3. **Reactive query hook:** `useBlazeQueryState({ prefix, tags, ttlRange, keys, limit, cursor,
includeValues })` → `{ items, nextCursor, loadMore, refresh }`, re-running on mutations
   through the **shared multiplexer**, not a provider-local listener. `ttlRange` is the 0.5.0
   expiry filter, deliberately not `ttlMs` (the write stamp); `keys` is the allow-list.
   Reactive queries **require `createCache({ indexes: true })`**: with indexes off the hook
   throws a setup error at mount naming the option — no silent O(n) `fullScan` path. Cursors
   follow the 0.5.0 rule (last-key anchor, survives deletion of the anchor key, no reset on
   mutation); `refresh()` restarts from page one. In tiered mode the hook calls
   **`queryAsync()`** instead of `query()` and warns that a sync query would be partial.
4. **Async/tiered hook (flagged sub-scope):** `useBlazeAsyncValue(key)` → `BlazeAsyncState<V>`
   for 0.5.0 tiered mode, using React Suspense/`use()` where available with a
   `{ suspended: false }` fallback for React 18. Sync hooks return `undefined` on a tiered
   miss. Removed entirely if tiered did not ship in 0.5.0.
5. **Imperative helpers:** `useBlazeSet`, `useBlazeInvalidate`, `useBlazeFlush`.
6. **Cleanup:** subscriptions torn down in effect cleanup, including StrictMode's double
   mount/unmount **and** concurrent transitions/Suspense retries (a retry must not leave the
   previous attempt's listener behind).
7. **Conformance adapter + type tests:** ~50-line `/testing` adapter; `expect-type`/`tsd`
   cases for `useBlazeValue<V>` generics and ESM consumption under `moduleResolution:
bundler` and `node16`.
8. **Example + docs:** `examples/react` Vite playground; README distinguishing this package
   from `@blaze-cache/react-query` and `@blaze-cache/swr`.

**Acceptance criteria:** `0.6.0-beta.1` published; conformance suite green; React 18/19 and
StrictMode + concurrent-transition tests pass; type tests pass; existing packages unchanged.
**Before beta.2:** bundle-size budgets and duplicate-instance CI checks are live.

## Stage 2 (0.6.0-beta.2) — Next.js bindings

Create `@blaze-cache/next` (peer: Next 14/15 App Router, plus React and integration-core).

1. **Client provider:** `<BlazeCacheProvider initialSnapshot={...}>` — the cache is created in
   an effect on the client only; nothing imports the wasm binary on the server.
2. **Server→client bridge:** there is no cache on the server. An **App Router server
   component or route handler** (not a SvelteKit-style `load`) passes plain records to
   `makeSnapshotFromRecords(records)` from `@blaze-cache/integration-core/snapshot` — a
   subpath with **no runtime `@blaze-cache/core` import**, so the server-bundle check stays
   green. The client provider calls `restoreSnapshot(cache, snapshot)` before first paint.
   `useBlazeHydrated()` flips true only after both the snapshot restore and the IDB hydrate
   have been applied and reconciled (see Foundation item 7 for ordering and write rules).
3. **Cross-request isolation test:** two concurrent server renders with different caches must
   never see each other's records — no module-level singletons anywhere in the path.
4. **Client fetch helpers:** `withBlazeFetch` built on `@blaze-cache/fetch`, stamping the
   hierarchy tag `next:route` (parent `next`, grandparent `framework`) so
   `cache.invalidateTags('next:route')` behaves like a client-side `revalidateTag`.
5. **SSR parity harness:** the Next example renders identical server HTML and first client
   pass; Playwright asserts no hydration warnings and that the snapshot seeds the cache. A
   build-time check fails if any server bundle imports `@blaze-cache/core` or
   `@blaze-cache/core/wasm` — the server may import only
   `@blaze-cache/integration-core/snapshot` and `@blaze-cache/core/shared`.

**Acceptance criteria:** `0.6.0-beta.2` published; Next example green in dev and production
build; hydration/parity/cross-request tests pass; no wasm or IndexedDB access on the server.

## Stage 3 (0.6.0-beta.3) — Vue and Pinia

Create `@blaze-cache/vue` (peer: Vue 3.5+) and `@blaze-cache/pinia` (peer: Pinia 2/3).

1. **Vue plugin:** `createBlazePlugin(cacheOrOptions)` → `app.use(...)`; `useBlaze()` injects
   the cache. Cleanup via `getCurrentScope()` / `onScopeDispose`; no wasm at import time.
2. **Vue composables:** `useBlazeValue(key)` returns a **`shallowRef`** so cached objects are
   not deep-proxied (identity preserved); `useBlazeQuery({ prefix, tags, ttlRange, keys, ...
})` returns a shallowRef of paged items plus `nextCursor`/`loadMore`/`refresh`;
   `useBlazeTag(tag)` for tag-driven recomputation. Query composables require
   `indexes: true` and throw a setup error otherwise; cursors follow the 0.5.0 last-key rule
   (survive anchor deletion, `refresh()` restarts); tiered mode uses `queryAsync()`.
   **Document that in-place mutation
   of a cached object will not trigger an update — callers must replace the value — and expose
   a `trigger()` helper wrapping `triggerRef` as the explicit escape hatch.**
3. **Pinia plugin:** `blazePiniaPlugin` persists selected stores. Declare via store options
   (`blaze: { key, ttlMs, tags, pick }`), write through `$subscribe` with `detached: true`,
   and hydrate with `$patch` **before** the first client render. The hydration guard is a
   **restore contract**: the patch uses the internal non-persisting, non-broadcasting,
   insert-if-absent path (or `storedAt` comparison), and the `$subscribe` writer stays
   disabled until it completes — so a restore neither re-writes storage nor broadcasts to
   other tabs (loop prevention + no stale overwrite).
4. **Namespacing:** keys `pinia:<store>$<id>`, tags `framework` → `pinia` → `pinia:<store>`;
   `purgeBlazePinia()` uses the shared scoped purge helper.
5. **Conformance adapters + docs:** ~50-line adapters for both packages; READMEs covering
   shallow-ref replacement semantics and the Pinia hydration guard.

**Acceptance criteria:** `0.6.0-beta.3` published; conformance suite green for both;
identity, scope-disposal and Pinia restore-loop tests pass; Vue 3.5 + Pinia 2/3 peer matrix.

## Stage 4 (0.6.0-beta.4) — Svelte and SvelteKit

Create `@blaze-cache/svelte` and `@blaze-cache/sveltekit`.

1. **Svelte stores (compatibility path):** `setBlazeContext(cache)` in the root component and
   `blazeStore(key)` (readable store over `subscribeValue`); `blazeQueryStore({ prefix, tags,
ttlRange, keys, ... })` for paged results with `nextCursor`/`loadMore`/`refresh` (requires
   `indexes: true`, throws otherwise; last-key cursors, tiered mode uses `queryAsync()`).
   Target Svelte 4/5 store compatibility; `onDestroy` removes listeners.
2. **Svelte 5 runes path — start the spike in beta.1, not here.** Runes use **deep proxies by
   default**, which is exactly the identity hazard. Use **`$state.raw`** for cached values
   (never plain `$state`) and `createSubscriber` from `svelte/reactivity` for the rune-native
   subscription path. The conformance suite runs in **runes mode specifically** with an
   identity assertion, so a future refactor to `$state` fails CI.
3. **SvelteKit SSR:** `hooks.client.ts` initialises the cache only when `browser` is true;
   `+layout.svelte` installs the context; a `load`-function snapshot is handed to the client
   through the shared safe bridge. Playwright asserts SSR/first-client parity, no hydration
   warnings, and no wasm in the server bundle.
4. **Conformance adapters + docs:** adapters for classic-store and runes-mode reads; READMEs
   covering `$state.raw`, store-vs-runes choice and SSR boundaries.

**Acceptance criteria:** `0.6.0-beta.4` published; conformance suite green in both modes;
SvelteKit SSR parity; Svelte 4/5 matrix; SvelteKit cannot ship if Svelte is dropped.

## Stage 5 (0.6.0-beta.5) — Solid

Create `@blaze-cache/solid` (peer: Solid 1.9+, plus integration-core).

1. **Client-only by contract:** the binding **throws a clear error on the server** (guard via
   `isServer` from `solid-js/web`). SolidStart is explicitly 0.7.0; plain `renderToString`
   with this binding is not supported. The guard itself is tested.
2. **Primitives:** `BlazeProvider` via Solid Context; `useBlaze()`; `createBlazeValue(key)` →
   `Accessor<V | undefined>` backed by `createSignal` and `subscribeValue` (Solid signals
   already compare by reference); `createBlazeQuery({ prefix, tags, ttlRange, keys, ... })` →
   resource-style accessor with paging and `refresh()` (requires `indexes: true`, last-key
   cursors). **Flagged sub-scope:** the `createResource`/`getAsync()`/`queryAsync()` path and
   the `BlazeAsyncState<V>` eviction behavior drop with tiered mode; the synchronous accessor
   and the state shape itself remain.
3. **Cleanup:** every primitive registers `onCleanup`; conformance suite asserts zero
   listeners after owner disposal.
4. **Example + docs:** `examples/solid`; README covering client-only scope and signal identity.

**Acceptance criteria:** `0.6.0-beta.5` published; conformance suite green; cleanup and
server-guard tests pass; Solid 1.9 matrix. **Feature freeze.**

## Release tooling — fixed/lockstep versioning

Eight packages ship as one unit. Adopt **Changesets** (or an equivalent fixed-version group)
with `@blaze-cache/integration-core` and every binding in one fixed group at `0.6.0`. Add a
**publish-order check** to CI and the `publish` script: `integration-core` must be resolvable
on the registry at the group's version before any dependent is published. Topological
`pnpm -r publish` is necessary but not sufficient — verify it explicitly rather than relying
on ordering alone.

## Cross-cutting guardrails

- Every new package is ESM-only, `sideEffects: false`, depends on `@blaze-cache/core` via
  `workspace:*`, declares its framework **and** `@blaze-cache/integration-core` as peers, and
  has a measured gzipped size budget enforced from beta.2 onward.
- **Teardown is part of the contract:** unmount leaves zero listeners; the conformance suite
  enforces it everywhere, including StrictMode and Solid owner disposal. See Risks for what
  happens when it regresses.
- No framework binding imports wasm or touches IndexedDB at module scope; all initialisation
  is client-side and lifecycle-bound. Server snapshots are per-request, built from records
  through `integration-core/snapshot`, and may use `core/shared` — but never core's root or
  wasm entry. Redaction is deny-by-default from the shared subpath.
- By-reference values are never deep-cloned, proxied or structurally compared: Vue
  `shallowRef` + replacement semantics, Svelte `$state.raw`, Solid signals. Identity is a
  conformance assertion, not an aspiration. `includeValues: true` deliberately hands live
  by-reference objects to UI code — document that contract and cap it with
  `maxEntries`/`maxValueBytes`; devtools-style summarization is **not** applied.
- Reactive queries require `indexes: true` and throw a setup error at mount when it is off —
  no silent O(n) `fullScan` path. Cursors are last-key anchors; `refresh()` restarts.
- Snapshot restores and Pinia `$patch` are non-persisting, non-broadcasting and
  insert-if-absent/HLC-compared; the IDB hydrate reconciles after the first-paint restore.
- All bindings share the integration-core envelope, key encoding, tag hierarchy and
  versioned snapshot format; unknown versions degrade to "no snapshot".
- Keep `pnpm lint`, `bench:ci` (with `indexes: true` and a binding attached), allocation tests
  and all Rust/wasm/JS suites green at every beta; update READMEs and the docs index in the
  same stage as the code.
- Scope valve: each framework family from beta.2 onward is droppable to 0.7.0 subject to the
  dependency table — never slip `rc.1` for one framework.

## Risks

- **Hydration mismatch / cross-request leakage (highest):** mitigated by explicit
  `getServerSnapshot` from restored state, per-request snapshots, client-only wasm init and
  Playwright parity/concurrency tests.
- **Deep reactivity breaking identity:** Vue deep refs and Svelte 5 `$state` proxies mutate
  semantics. Mitigated by `shallowRef` and `$state.raw`, with identity tests in the
  conformance suite. A regression that fails teardown or identity is a release blocker
  because the Rust drop log stays enabled and leaks listeners.
- **Dual-instance skew:** two copies of integration-core diverge on kind guards and listener
  registries. Mitigated by peer dependency + global-symbol version guard + CI duplicate
  resolution check.
- **Tiered async semantics:** sync APIs return `undefined` on a wasm miss; the shared
  `BlazeAsyncState` keeps error/pending and evict-vs-invalidate handling consistent. Dropped
  with the flagged sub-scope if tiered is absent from the 0.5.0 baseline.
- **Peer dependency churn:** React 18/19, Next 14/15, Svelte 4/5, Pinia 2/3 and Solid 1.9
  need real matrices in CI, not a single latest-version install.
- **Baseline dependency:** handled at the go/no-go checkpoint before beta.1 — no work starts
  before `0.5.0-rc.1`, and tiered is a flagged sub-scope, never new core work in 0.6.0.
- **Restore-as-write:** a naïve snapshot restore would broadcast through 0.4.0 sync and flush
  older data over newer IndexedDB rows. Mitigated by insert-if-absent/HLC comparison plus the
  internal non-persisting, non-broadcasting path; covered by the rc.1 Restore safety gate.

## Sequencing priorities

1. **Land the 0.5.0 interface changes before beta.1 ships** — `invalidate.tags`, `ttlRange`,
   `keys` allow-list, indexes-off throw, `includeValues` caps, `queryAsync()`, and the
   `@blaze-cache/core/shared` wasm-free subpath. They are free now and breaking later.
2. **Resolve the cross-doc contradictions first** — tiered fallback (0.5.x/0.7.0, never 0.6.0)
   and multi-GB renumbering (0.7.0) are settled in both plans.
3. **Confirm the 0.5.0 baseline at the go/no-go against the Baseline contract** — devtools and
   query stable at `rc.1`; tiered status decides whether the flagged sub-scope ships here or
   becomes an additive 0.6.x.
4. **Fix the server snapshot design** — record-based `makeSnapshotFromRecords`, the
   `integration-core/snapshot` core-free subpath, and restore-as-non-write semantics.
5. **Build integration-core with the per-cache multiplexer, conformance harness and one async
   state shape in beta.1** — this is what makes every later gate mechanical.
6. **Start the Svelte 5 runes spike during beta.1**, in parallel with React/Next, because it
   carries the highest design uncertainty even though Svelte ships in beta.4.
7. **Land bundle-size budgets and duplicate-instance CI checks before beta.2**, so they do not
   become rc.1 surprises.

## Framing: validate the premise first

Before committing to large architectural work, one correction matters. The headline
bottleneck in the original proposal — *serializing raw JS objects across the Wasm
boundary* — **does not currently exist**. Values are `JsValue` externrefs held by
reference in the Rust slab; `get`/`set` never clone or serialize them
(`crates/blaze-cache-wasm/src/lib.rs:81–125`, documented contract at
`packages/core/src/cache.ts:131–143`). The residual cost is the **boundary crossing
itself** (key marshalling, tag `Vec<String>` marshalling), and a key scratch buffer
already removes ~13 ns of that on repeated keys (`packages/core/src/wasm.ts:86–189`).

So: treat the hybrid-memory idea as a *hypothesis to test with benchmarks*, not a
foregone conclusion. This is why benchmarks are Stage 1 and gate Stage 2.

Today's state at a glance:

| Area | Current reality |
|---|---|
| Memory | Values by-reference externrefs in Rust; keys already have a raw/zero-copy path; no bytes/binary value mode |
| Benchmarks | Two Node-only microbenchmark suites; honest caveats but no browser, no payload-size matrix, no persistence/hydration; root README benchmarks section is mislabelled (`README.md:1289–1318`) |
| Multi-tab | None. IndexedDB `onversionchange` reopen only; documented "last-writer-wins, no coordination" workaround (`cache.ts:190–200`, `README.md:666–675`) |

## Stage 1 (0.4.0-beta.3) — Real-world, published benchmarks

**Goal:** numbers developers can trust, and a baseline that tells us whether Stage 2
is worth building.

**Steps**

1. **Extend `benchmarks/cache`** (`runner.mjs`, `harness.mjs`, `scenarios.mjs`,
   `adapters.mjs`) with a payload-size matrix: tiny (≤64 B), small (~1 KB), medium
   (~10 KB), large (~100 KB), massive (~1 MB), both structured-cloneable objects and
   `Uint8Array`. Reuse the existing deep-equality probe check and calibrated
   median/spread methodology.
2. **Add the missing scenarios** the framework suite itself calls for
   (`benchmarks/framework/README.md:25–31`): TTL-expiry-heavy churn, eviction under
   pressure, tag invalidation at scale, persistence flush, hydration from IndexedDB.
3. **Add a browser benchmark workspace** (`benchmarks/browser/`, Vite + Playwright) so
   numbers reflect the actual deployment target — crossing the Wasm boundary in a real
   browser. Keep Node suites for CI regression; publish browser numbers for trust.
4. **Compare against the right peers:** `lru-cache` (named in the original proposal),
   `quick-lru`, plain `Map`, and `@tanstack/query-core` / SWR where applicable. Keep the
   "full-featured" scenario (TTL + tags + eviction) as the headline, but always publish
   the feature-equivalent table next to it.
5. **Publish a results page** with methodology, hardware, versions, raw JSON outputs
   (`--json` already exists), and the explicit caveat about `set` boundary costs. Fix
   the stale/mislabelled root README section while doing so.
6. **CI:** add a `bench:ci` job that runs `--quick` and fails on >20% regressions against
   a checked-in baseline, so perf work isn't guesswork.

**Acceptance criteria:** published results page; 5 payload sizes × 5 scenarios in both
Node and browser; no unqualified "faster than JS" claim that the data doesn't support.

**Status (2026-11-20): complete.** The Node suite now runs ten scenarios across 5 payload sizes
× 2 value representations; the Vite + Playwright browser workspace runs the identical suite in
Chrome; `lru-cache` joined the peer set; the root README section was corrected; a `bench:ci` job
gates >20% scenario-normalised regressions against a checked-in baseline; and the results and
raw JSON are published at [`docs/benchmarks/RESULTS.md`](../benchmarks/RESULTS.md). The matrix
shows no payload-size cliff: the *serialisation* premise is not supported. The residual crossing
cost is real (it is why blaze is slower than native LRU peers on the write path) but small in
absolute terms, so any Stage 2 work must be justified by that measured delta — not by object
copying that does not happen.

## Stage 2 (0.4.0-beta.3) — Hybrid memory / zero-copy options

**Gate:** proceed only if Stage 1 shows the boundary materially hurting real payloads.
Implement behind an opt-in option; measure before and after; keep current behavior as
default.

**A. True zero-copy for binary values (narrow, high confidence).**

Add a "bytes" value mode: `setBytes(key, ArrayBufferView)` stores the payload directly
in Wasm linear memory as `(offset, length)` with no serialization, and `getBytes`
returns a view onto it. This is the only way to get *genuine* zero-copy for JS values,
because arbitrary objects can't live in linear memory without serialization.

- Risks to design around: `memory.grow` detaches views — either pin/grow with headroom
  and document view lifetime, or return copies for long-lived reads.
- Validate all offsets through a safe helper (mirroring `with_raw_key`,
  `crates/blaze-cache-wasm/src/lib.rs:454–474`) — both crates `forbid(unsafe_code)` and
  release panics are `abort`.
- Add allocation tests alongside `crates/blaze-cache-core/tests/allocations.rs`.

**B. JS-authoritative hybrid mode (broad, needs measurement).**

Move the value store into a fast JS-side `Map`, leaving Rust/Wasm with keys, TTL, tags,
SIEVE bookkeeping, and eviction decisions:

- `set`: write JS `Map` + Wasm metadata; `get`: Wasm hit/miss → `Map.get`.
- Eviction/expiry: extend the existing drop-log drain
  (`packages/core/src/cache.ts:1529–1566`) to emit evicted **keys/ids** so JS deletes
  from its `Map`.
- Further optimization: give entries a numeric slot id and let JS hold
  `Map<key, id>` + `Map<id, V>`, so hot hits call Wasm by id and never marshal a key
  string at all.
- **Must preserve:** by-reference value semantics, tag invalidation, `entries()` /
  `entry()`, stats, persistence reconciliation, and the zero-allocation tests.
- Opt-in via `storage: 'js' | 'wasm'` so existing users are unaffected.

**Acceptance criteria:** A and/or B shipped behind a flag; benchmark delta published
from Stage 1; all existing Rust/wasm/TS suites green; docs updated with the
ownership/memory tradeoffs.

**Status (2026-11-21): both shipped, opt-in, measured.** A adds `setBytes`/`getBytes`/
`getBytesCopy` backed by a safe, chunked linear-memory arena (`blaze-cache-core/src/bytes.rs`)
with `(ptr, len)` validation mirroring `with_raw_key`, `Drop`-based region reuse and allocation
tests. B adds `storage: 'js'` with stable per-entry ids (never reused across slab reuse),
by-id hit/peek/has APIs, ids in the drop log, and a JS `Map<id, V>` — preserving by-reference
semantics, events, tag invalidation, `entry()`/`entries()`, stats and persistence. Neither
mode is the default. The measured deltas
([`docs/benchmarks/RESULTS.md#stage-2-measured-deltas`](../benchmarks/RESULTS.md)) show B is
slower and A is a capability rather than a perf win, so the Stage 1 gate remains respected:
no unqualified performance claim is made for either.

## Stage 3 (0.4.0-beta.3) — Multi-tab synchronization

**Goal:** remove the documented "no coordination between tabs" limitation with an
opt-in, production-safe sync layer.

**Design**

1. **Opt-in config:** `multiTab: { enabled: boolean, channel?: string, strategy?: 'value' | 'invalidate' }`.
   Default off — preserves current behavior and perf.
2. **Channel:** one `BroadcastChannel` per `namespace\0generation` (reuse the existing
   IDB key encoding, `persistence/indexeddb.ts:100–111`), with a per-instance
   `clientId` (`crypto.randomUUID()`). Ignore own messages; validate `event.origin` /
   channel name.
3. **Protocol:** messages for `set`, `delete`, `clear`, `invalidate-tags`, `rotate`,
   plus a `hello` / `state` handshake on `visibilitychange`/focus. Each carries
   `{ clientId, seq, key(s), ttlMs, tags, hlcTimestamp, value? }`.
4. **Ordering:** hybrid logical clock + per-client sequence + deterministic `clientId`
   tiebreaker for last-writer-wins. Store a per-key version so a late-arriving stale
   message never overwrites a newer local value — this directly fixes the "hidden tab
   flushes an older value" failure in `cache.ts:196–200`.
5. **Value vs invalidate strategy:** broadcast structured-cloneable values by default
   (BroadcastChannel uses structured clone); for non-cloneable values, fall back to an
   invalidate message. `strategy: 'invalidate'` sends only tombstones for apps that
   refetch on focus.
6. **Echo prevention:** apply remote mutations through an internal path that updates
   Wasm + `Map` but bypasses `#notify`'s publish step, so remote writes don't
   re-broadcast or trigger duplicate IDB flushes. Fire new remote events
   (`remote-set`, `remote-delete`, etc.) so apps can observe cross-tab changes.
7. **IDB write coordination:** use `navigator.locks.request` (Web Locks) around flush,
   or skip flushing keys whose local version is older than the last remote version
   seen. Keep the existing `onversionchange` handling.
8. **Lifecycle:** close channel and flush on `dispose`; handle `pagehide` /
   `visibilitychange`; degrade silently when `BroadcastChannel` is unavailable
   (Web Workers / older browsers).

**Tests:** Node's global `BroadcastChannel` lets us simulate two cache instances as two
tabs — assert propagation, stale-message rejection, tag invalidation, dispose cleanup,
no echo loops. Update the "Multiple tabs" README section from "limitation + workaround"
to "feature + configuration".

**Acceptance criteria:** two simulated tabs stay consistent across
set/delete/clear/invalidate/rotate; the hidden-tab stale-write scenario from the docs is
provably fixed; zero echo storms; feature off = byte-for-byte current behavior.

**Status (2026-11-21): complete.** Added `packages/core/src/multitab.ts` with a BroadcastChannel
per `namespace\0generation`, HLC + per-client sequence + client-id ordering, per-key version
guard, `hello`/`state` handshake, value/invalidate strategies with a structured-clone fallback,
remote-only events, a Web Lock around flush, and silent degradation where BroadcastChannel is
missing. Wired behind `multiTab.enabled` (off by default) with six simulated-tab tests in
`packages/core/test/multitab.test.mjs`, including the hidden-tab stale-write regression and
echo prevention. Root and package READMEs now present multi-tab as a feature.

## Stage 4 (0.4.0-beta.3) — Final speed optimization (data-driven)

**Goal:** close the gap that the measurements actually show — the **write path** — without
changing any default semantics. This is the final stage before release; it is deliberately a
*targeted tuning* stage, not a redraw of the architecture. Stage 2 already proved that moving
values out of the slab does not help, so this stage works on the boundary costs that Stage 1
and Stage 2 measured.

**Evidence from Stages 1–2**

* `full-featured` — the headline — is where blaze pays: roughly 1.7× slower than
  `QuickLRU + tag index` in Node and 2.2× in the browser, while beating the hand-rolled
  three-layer stack by a smaller margin. The gap is on the **write half**: every `set` crosses
  the boundary and marshals a key, a deadline and a `Vec<String>` of tags.
* `fill` shows the same cost in isolation, but `get-hit` does **not**: blaze's read path pays
  no comparable premium once the key scratch is warm. Optimising reads further would chase a
  number the data says is already competitive.
* Payload size does not move either curve (Stage 1 matrix), so **no optimisation may be
  justified by "large objects are slow to serialise"** — that premise was disproven.
* Stage 2's `storage: 'js'` is slower than the default on every measured workload; the JS
  `Map` adds work the key scratch already avoided. Its by-id APIs are kept as an opt-in
  capability, not as a speed story.

**Steps**

1. **Tagged raw-key write path.** Today `setRaw` (pre-encoded key) exists only for untagged
   writes; a tagged write pays a fresh `passStringToWasm0` key allocation **and** a
   `Vec<String>` tag crossing. Add a raw variant that takes the key from `KeyScratch` and tags
   from a shared flat buffer plus offsets, so the headline workload stops allocating per
   `set`. Validate every offset through safe helpers (`with_raw_key`, clamped tag ranges) —
   both crates stay `forbid(unsafe_code)`.
2. **Bulk-write tuning.** Extend the same encoding to `setMany`/`setManyRaw`, so a batch of
   tagged writes does one boundary crossing with no per-entry key allocation or tag vector,
   while still refreshing TTL/tags and returning correct drop events. Reuse the drop-log
   drain from Stage 2B (ids + keys) so JS-owned values stay in sync.
3. **Tag-marshalling and drop-log overhead.** Intern frequently repeated tag names at the
   boundary (numeric ids with a small string table) only if the benchmark shows the
   `Vec<String>` copy is material; keep `invalidateTags` returning the exact removed keys for
   persistence. Trim the id-only drop drain in JS mode to avoid building full entry objects
   when only `id`/`key` are needed — while keeping `evict`/`expire` events carrying the real
   value.
4. **Bytes producer path.** Add an internal `setBytesPtr`-style entry point for callers that
   already wrote into the arena (e.g. a decoder writing straight into Wasm memory), so they
   do not pay the extra JS→Wasm copy. Keep the public `setBytes(key, ArrayBufferView)` API and
   its view-lifetime contract unchanged; document the new path as advanced/opt-in.
5. **Re-measure before keeping anything.** For every change, run the full Node matrix and the
   browser workspace, publish a before/after table and the raw JSON next to the Stage 1/2
   results, and keep only changes that improve `fill` or `full-featured` **without** regressing
   the feature-equivalent table or any other scenario beyond the spread. `bench:ci` is the gate;
   a change that cannot show a delta is dropped, not shipped with a story.

**Guardrails specific to this stage**

* No change to value ownership, default `storage`, TTL semantics, SIEVE behaviour, tags or
  event payloads — this stage is invisible to users except for speed.
* No unqualified "faster than JS" claim; every published number sits beside its
  feature-equivalent peer and its spread.
* If none of the above produces a measurable win, the stage closes with a documented negative
  result and the release proceeds — a tuning stage must never become a rewrite.

**Acceptance criteria:** at least one write-path scenario (`fill` or `full-featured`) measurably
faster in **both** Node and browser versus the Stage 2 baseline, no other scenario regressed
beyond its spread, `bench:ci` green, all Rust/wasm/TS/integration/allocation suites green, and
the results page updated with before/after deltas. If the gate is not met, the stage is closed
with that recorded outcome instead.

**Status (2026-11-22): complete, narrowly.** Tagged raw writes are opt-in internally (used
automatically when the wasm exports the new bindings), with a single-tag fast path, a batched
`setManyRaw`, safe pointer/offset validation and 3 new wasm tests; `setBytesReserved` exposes
the advanced producer path. Same-run A/B shows `full-featured` 2% faster in Node (175.3 → 171.4)
and 4% faster in Chrome (190.1 → 182.8), with `fill` flat/slightly slower and `get-hit`
unchanged. Tag-name interning was deliberately skipped as unjustified by the data. All suites
and `bench:ci` are green; deltas and raw JSON are in
[`docs/benchmarks/RESULTS.md#stage-4-final-speed-optimization-beforeafter`](../benchmarks/RESULTS.md).

## Stage sequence (all under 0.4.0-beta.3)

| Stage | Work | Why |
|---|---|---|
| 1 | Benchmarks: extend + browser workspace, baseline JSON | Grounds every later decision; fixes stale docs |
| 2A | Bytes / zero-copy mode — if large-payload data justifies it | Narrow, self-contained, high confidence |

## Cross-cutting guardrails

- Keep both crates `forbid(unsafe_code)`, validate all host inputs, preserve the
  by-reference contract as default.
- Keep every new capability opt-in and backward-compatible.
- Keep CI (`rust.yml`, `js.yml`, `lint`, allocation tests) green at every stage.
- Update `README.md` and per-package docs in the same stage as the code they describe.

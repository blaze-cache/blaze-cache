# Blaze Cache — 0.5.0 Roadmap (Developer Tools + Large-Data Core)

**Date:** 2026-11-20
**Revised:** 2026-11-23 — added the query/tiered-storage track. Devtools remains a
first-class part of the release; beta.4 is the only conditional stage.
**Target release:** `0.5.0`
**Baseline:** `0.4.0` (depends on the `0.4.0-beta.3` stages in
[`0.4.0-roadmap.md`](0.4.0-roadmap.md))
**Scope:** new `@blaze-cache/devtools` packages, in-app UI, cross-tab monitoring, indexed

## Version ladder — beta to final test

`0.5.0` ships through five prerelease gates. Each gate has an exit criterion; the next
stage starts only when the previous one is green. **Devtools is a first-class, non-droppable
part of this release**: its workstream lands in `beta.1`–`beta.3` and is frozen at `beta.3`.
The core track (query + tiered storage) shares those gates and finishes at `beta.4`, which is
the release's only conditional stage.

tiered as a finished dependency and would double in scope. **Devtools is never the thing
that gets dropped.**

## Goals and non-goals

**Goals**

- See every cache instance in the app: size, capacity, hit rate, TTLs, tags, persistence
  state, and a live event feed — without instrumenting application code.
- Perform actions from the panel: inspect, set, delete, clear, invalidate by tag, prune,
  touch/TTL, flush, hydrate, rotate generation, reset stats.
- Understand behavior across tabs: which tab wrote a key, stale-write rejection via 0.4.0's
  HLC ordering, and what IndexedDB is doing.
- Keep the production hot path untouched when devtools is off.
- Query entries by key prefix, tags and TTL with paged, bounded results instead of scanning
  the whole cache.
- Keep an offline dataset larger than memory usable: IndexedDB is the source of truth, the
  wasm cache is a bounded working set.

**Non-goals (explicitly out of scope for 0.5.0)**

- A full Chrome/Firefox extension with a DevTools panel — the transport is designed for
  it, but the extension UI ships after 0.5.0.
- Time-travel debugging, replay, or snapshot persistence to disk.
- Changing cache semantics, eviction policy, or the by-reference value contract.
- Making `get()` async by default — tiered mode exposes an explicit `getAsync()` instead.
- Multi-GB streaming hydration and compaction: 0.5.0 targets roughly 1M metadata rows and
  hundreds of MB with a bounded working set; true multi-GB is a 0.7.0 follow-up (also listed
  in 0.6.0's non-goals).
- Full-text or fuzzy search, SQL-like joins, or query pushdown — this is key/tag/TTL
  filtering only.

## Extension points in the current codebase

The devtools core attaches to surfaces that already exist; no core API redesign is needed:

| Need               | Existing surface                                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Instance discovery | Explicit `attach(cache)` (no global registry exists — `types.ts:69–72` already anticipates devtools)                                                                    |
| Live mutations     | Wildcard `on(listener)` + 10 `CacheEventType` values (`types.ts:104–114`, `events.ts:58–284`)                                                                           |
| Evict/expire       | Drop log via wildcard subscription → `CacheEventBus.wantsDrops` / `#syncDropTracking` (`cache.ts:214, 1560–1566`)                                                       |
| Metrics            | `stats(): CacheStats` with `hits, misses, evictions, expirations, invalidations, size, capacity, hitRate` (`cache.ts:474–478`, `types.ts:46–56`)                        |
| Contents           | `keys()`, `entries()`, `entry(key)`, `ttl(key)`, `tagsOf(key)`, `keysWithTag(tag)` (`cache.ts:426–456`)                                                                 |
| Persistence        | `persistence.stats()` — 15 fields incl. `pending, flushes, recordsWritten, errors, lastFlushAt` (`persistence/types.ts:135–166`, `cache.ts:1423–1440`)                  |
| Cross-tab          | 0.4.0 BroadcastChannel sync with `clientId` + HLC ordering (`0.4.0-roadmap.md`, Stage 3)                                                                                |
| Zero-cost gate     | `CacheEventBus.hears/size/wantsDrops` (`events.ts:63–99`) — no listeners means no drop log and no snapshot work                                                         |
| Event payload      | 0.5.0 makes an **additive** change: `invalidate` gains `tags: string[]` beside `keys`; keyless `remote-invalidate` means "broad revalidate — anything may have changed" |
| Shared contract    | `@blaze-cache/core/shared` — a wasm-free, server-safe subpath holding redaction patterns, the `BlazeRecord` envelope guard and the `binding:feature` kind convention    |
| Query              | Opt-in indexes + `query()` with `ttlRange`/`keys` allow-list/`includeValues`; sync and memory-only (Stage 1); snapshots and panel read bounded pages                    |
| Disk queries       | IDB schema v2 with `tags`/`expiresAt` indexes and metadata-only paged `scan()` (Stage 2); v1 rows migrated in place                                                     |
| Tiered storage     | `tiered`/`maxBytes`, `getAsync()` and `queryAsync()` beside the sync APIs, disk-authoritative values (Stage 4)                                                          |

**Critical constraint:** `entry()`/`entries()` return **live by-reference values**
(`cache.ts:131–143`). Devtools must never hand those to the UI directly: snapshot through
a safe summarizer (`structuredClone` in try/catch, size/depth caps, fall back to a type
label), and redact keys matching secret patterns (the identity-key collision fix in
`d175f6a` is a reminder that cache keys can carry credentials). The query API's
`includeValues: false` default and `maxEntries`/`maxValueBytes` caps exist to enforce the
same rule for large datasets. `includeValues: true` deliberately returns **live by-reference
values** — that is the contract, and it is permitted only together with `maxEntries`/
`maxValueBytes` caps; devtools never exposes it to the UI.

## Stage 1 (0.5.0-beta.1) — Observability + query core

Create `@blaze-cache/devtools` following existing package conventions (plain `tsc`,
`src/*.ts` + `index.ts` barrel, `test/*.test.mjs` with `node:test`, package README with
the standard logo header).

1. **Registry & lifecycle:** `attach(cache, { label? }) -> handle`, `detach`, `list`,
   `dispose`. Attach registers wildcard event listeners and keeps a weak reference to
   the instance; `dispose()` removes all listeners so the drop log switches back off.
2. **Versioned protocol:** `{ protocol: 1, tabId, clientId, cacheId, ts, kind: 'snapshot' | 'event' | 'action', payload }`.
   Types exported from `src/protocol.ts` so future transport implementations share them.
3. **Snapshot builder:** on demand (never on the hot path) — `stats()`, `size()`,
   `capacity()`, `keys()`, summarized `entries()`, per-key `ttl`/`tags`,
   `persistence.stats()`. Cap entries and payload bytes (`maxEntries`, `maxValueBytes`)
   with explicit truncation markers.
4. **Safe summarizer:** clone-or-describe values; handle `BigInt`, `Map`, `Set`,
   `ArrayBuffer`, `Uint8Array`, cyclical objects, functions, and non-cloneable externrefs;
   never throw into the host app. Recognize `BlazeRecord` envelopes using the duck-typed,
   version-tolerant guard from `@blaze-cache/core/shared` — frozen here so 0.6.0 cannot
   redefine it — and display `kind`/`v`, deriving the framework from the
   `<binding>:<feature>` kind prefix, instead of expanding the payload.
5. **Event feed:** ring buffer (default 500) of the 10 event types, with key, timestamp,
   and tab/client attribution; `onEvent` subscription for UI consumers.
6. **Redaction:** default-on `redactKeys` patterns (e.g. `authorization`, `token`,
   `cookie`) and a `valueMode: 'summary' | 'none' | 'full'` option; `'full'` requires an
   explicit opt-in. The patterns live in `@blaze-cache/core/shared` — a wasm-free,
   server-safe subpath, not in devtools — so 0.6.0 bindings and server snapshots can reuse
   them without importing the core root, wasm entry or `@blaze-cache/devtools`.
7. **Zero-cost guarantee:** when no consumer is attached, no listeners, no snapshots, no
   timers. Verify with allocation/event-count tests.

### Core track (0.5.0-beta.1) — indexed queries in memory

Opt in at `createCache({ indexes: true })`. With it off, no extra structures are allocated
and the hot path is byte-for-byte unchanged.

1. **Indexes:** an ordered key index (`BTreeSet<String>`) for prefix/range scans; reuse
   `TagIndex` membership (`tags.rs`) for tag constraints; add an expiry-ordered index for
   TTL ranges. Maintain all three on insert/remove/touch/invalidate, bounded by `capacity`.
2. **Query API:** `query({ prefix, tags: { any, all, none }, ttlRange, keys, limit, cursor,
includeValues })` → `{ items, nextCursor, total? }`, plus `queryKeys()` and `count()`.
   `ttlRange` (not `ttlMs`, not `ttl(key)`) is the expiry filter. `keys` is an optional
   **allow-list**: only those keys are considered; with `includeValues: true` only their
   values are returned, capped by `maxEntries`/`maxValueBytes`. `includeValues: true`
   returns **live by-reference values** — the contract — and is permitted only with those
   caps; the default `false` returns metadata summaries only. `limit` is required. A
   `where?: (summary) => boolean` post-filter applies only over already-narrowed candidates
   and requires `fullScan: true` with no indexed constraint. **Without `indexes: true` and
   without `fullScan: true`, `query()` throws a clear setup error** — no silent O(n) scan;
   consumers can catch it. **Cursors are opaque last-key anchors in ascending key order:** a
   mutation does not reset an outstanding cursor (it survives deletion of the anchor key),
   pages re-read the live store, and a stable view calls `refresh()` to restart from page
   one. This is the rule reactive `loadMore` relies on.
3. **Wasm bindings:** `queryKeys(prefix, tagIds, ttlRange, limit, cursor)` validates all
   offsets through safe helpers, keeps both crates `forbid(unsafe_code)`, and never
   materialises the whole keyspace.
4. **Zero-cost proof:** allocation/event-count tests with indexes on and off; existing
   Rust/wasm/TS suites unchanged and green.
5. **Additive public API (beta.1):** the `invalidate` event gains `tags: string[]` beside
   `keys` (entries are already gone when a listener runs, so tags cannot be recovered from
   `tagsOf(key)`); a keyless `remote-invalidate` is defined as "broad revalidate — anything
   may have changed"; the new `@blaze-cache/core/shared` subpath is published. All are
   additive, so the "no changes to existing public APIs" criterion allows them.

**Wire-up:** add `"@blaze-cache/devtools"` to `tsconfig.base.json:24–33` path aliases;
`pnpm -r test` / `typecheck` pick up the package automatically once it defines those
scripts (`js.yml:33–89`). `query()` replaces `entries()` in the devtools snapshot builder
(step 3 above), so both tracks share one bounded-read implementation.

**Acceptance criteria:** `0.5.0-beta.1` published; unit tests for registry, protocol,
summarizer (including hostile/cyclic values) and zero-cost gate; query API covered by
cursor (incl. deleted anchor), prefix, tag, `ttlRange` and `keys` allow-list cases, the
indexes-off throw and the `fullScan` guard; `includeValues: true` enforces caps; additive
`invalidate.tags` and `@blaze-cache/core/shared` covered; allocation tests green with
indexes on and off; existing core tests unchanged and passing. "No changes to existing
public APIs" means no **breaking** changes — additive exports are allowed.

## Stage 2 (0.5.0-beta.2) — Actions + UI + disk queries

Create `@blaze-cache/devtools-react`: a React panel component plus a headless hook,
using only `workspace:*` dependencies.

1. **Headless hook:** `useDevtools()` → `{ caches, selected, snapshot, events, actions, attach, detach }`.
   Panel UI is optional — apps can build their own UI on the hook.
2. **Panel UI:** cache selector; overview cards (hits/misses/hit rate, size/capacity,
   evictions/expirations, pending flushes/errors); live event feed with filters; entry
   table with key, size, TTL countdown, tags, and a value inspector; persistence tab.
3. **Actions:** `get`/`peek`, `set` (JSON or text value, TTL, tags), `delete`, `clear`,
   `invalidateTags`, `prune`, `touch`, `flush`, `hydrate`, `rotate`, `resetStats`.
   Every action is attributed to a tab and reuses the same internal path as local
   mutations so 0.4.0 multi-tab sync broadcasts them.
4. **Safety:** confirmation for destructive actions (`clear`, `rotate`, `prune`);
   disable the panel automatically when `import.meta.env.PROD` unless
   `devtools: { enabled: true }` is explicitly set; keyboard shortcut to toggle.
5. **Examples:** wire the panel into all 7 Vite examples behind a dev-only flag; add a
   `dev:devtools` root script for a dedicated demo app.
6. **Docs:** package READMEs, root README section, and a "Devtools" guide with screenshots.

### Core track (0.5.0-beta.2) — disk-side queries

1. **Schema v2:** bump `SCHEMA_VERSION`/`DB_VERSION` in `persistence/indexeddb.ts`,
   migrating v1 rows through the existing `MIGRATIONS` map. Add a `tags` multiEntry index
   and an `expiresAt` index; keep the NUL-safe `ns\0key` primary key so prefix scans use
   `IDBKeyRange.bound(ns + prefix, ns + prefix + '\uffff')`.
2. **Out-of-line values:** move large payloads into a `values` store keyed by cache key,
   with the metadata row holding a size/ref. A metadata scan never structured-clones a
   value.
3. **`scan()`:** add paged `scan(filter, { cursor, limit })` to `CachePersistence` as an
   **optional** method, so custom adapters keep working unchanged. It always returns
   **metadata rows only** — no structured-cloned values. The async `queryAsync()` added in
   Stage 4 delegates to it; with `includeValues: true`, values load **lazily per page** via
   `peek()`/`getAsync()`, never for the whole result set.
4. **Panel integration:** the entry table and value inspector read `scan()` pages rather
   than `entries()`, so a 100k-entry cache does not build a 100k-row array in the UI.
5. **Benchmark harness:** add real-IDB flush/hydration scenarios to `benchmarks/browser/`
   (keep the in-memory rows for comparability; label both). The numbers land in beta.4.

**Acceptance criteria:** `0.5.0-beta.2` published; each action exercised in at least one
example and covered by an integration test; package READMEs complete; v1→v2 migration,
newer-schema safe reset and downgrade tests green; on-disk tag/prefix/expiry queries
verified not to read value blobs.

## Stage 3 (0.5.0-beta.3) — Cross-tab, hardening, browser tests

1. **Cross-tab aggregation:** relay `snapshot`/`event` messages over a dedicated
   BroadcastChannel per namespace; show a tab list with per-tab cache snapshots;
   attribute mutations via `clientId`; address actions to a specific tab (or broadcast).
   Respect 0.4.0's HLC ordering — devtools must not itself create stale writes. Cross-tab
   devtools must also assume tiered mode broadcasts **invalidation, not payloads** for
   large values: message handling must not depend on receiving the value.
2. **Transport abstraction:** `DevtoolsTransport` interface with an in-page default and
   a `PostMessageTransport` stub ready for a future browser extension. Protocol is
   versioned so mismatched builds degrade instead of crashing.
3. **Performance hardening:** throttle snapshots and event feed (e.g. 4 Hz, coalesced),
   virtualize the entry table, offload summarization to idle callbacks, and add a
   `maxTabs`/`maxEvents` cap. Re-run 0.4.0's benchmark suite with devtools attached vs
   detached; publish the overhead number honestly.
4. **Privacy/security:** default redaction reviewed; no network calls; CSP-friendly
   (no `eval`, no inline scripts); dependency audit (`cargo audit`, `pnpm audit`); extend
   `docs/security/` with a short devtools threat note (what the panel can see, what it
   redacts, how to disable in production).
5. **Browser test infrastructure:** add `benchmarks/browser/` and/or `tests/browser/`
   with Vite + Playwright (0.4.0 Stage 1 already proposes this workspace). Cover panel
   render, each action, two-tab propagation, and production auto-disable. Add a CI job
   in `js.yml` running Playwright with pinned browser versions. **Harness rule, settled now
   because 0.6.0 adds seven more examples:** every example runs in Chromium; only the
   SSR/hydration-parity subset runs in all three browsers (Chromium, Firefox, WebKit).
   This is also the harness beta.4 uses for real-IDB measurement.

**Acceptance criteria:** `0.5.0-beta.3` published; Playwright suite green in
Chromium/Firefox/WebKit; no redaction bypass found; overhead number published; docs
complete. **Devtools track frozen here.**

## Stage 4 (0.5.0-beta.4) — Tiered offline storage

Opt in through `persistence: { tiered: true, maxBytes }`. The first three gates must be
green; this is the release's only conditional stage (see the scope valve above).

1. **Metadata-only hydrate:** in tiered mode, `#hydrate` loads metadata rows only; values
   are fetched on demand. `get()` stays synchronous and memory-only; a new `getAsync(key)`
   does wasm-miss → IDB value load → insert into the working set → return. **Queries follow
   the same rule:** `query()` stays sync/memory-only and **warns that a bounded working set
   can yield partial results while disk holds more**; a new `queryAsync(filter)` beside it
   delegates to `scan()`. `get()`/`query()` never silently become async.
2. **Bounded working set:** SIEVE still governs the in-memory cache. Every dirty key is
   flushed to storage **before** eviction can drop it, so the bounded working set never
   loses data. Track approximate bytes; for opaque externrefs require an explicit
   `sizeHint` — JS object sizes are not observable, and that limitation is documented
   rather than guessed at.
3. **Quota & reclamation:** `navigator.storage.estimate()` / `persist()`, graceful
   `QuotaExceededError` degradation to memory-only (reusing the existing storage-failure
   fallback), and a disk-side LRU/TTL reclamation policy.
4. **Multi-tab:** tiered mode defaults to the existing `strategy: 'invalidate'` for large
   values — broadcast tombstones and HLC versions, not payloads — so a hidden tab cannot
   resurrect an older value or flood the channel.
5. **Measurement:** publish real-IDB flush/hydration numbers from the beta.3 harness into
   `docs/benchmarks/RESULTS.md`, with hardware, adapter and spread. `bench:ci` gates any
   tiered overhead; no unqualified perf claims.
6. **Docs:** root README "Core concepts"/"Persistence", package READMEs, and an explicit
   statement of the ~1M-row / hundreds-of-MB target and the 0.7.0 multi-GB follow-up.

**Acceptance criteria:** `0.5.0-beta.4` published; a dataset larger than `capacity` and
`maxBytes` works with bounded memory; no data loss on eviction, quota failure or tab
churn; tiered cross-tab tests green; real-IDB numbers published. **Core track frozen here.**
If this gate is not green, `beta.4` is dropped and the release proceeds to `rc.1` with
devtools + query intact.

## Risks and guardrails

- **Live-value aliasing:** devtools must not mutate cache contents via returned references —
  snapshot first, always. Covered by summarizer tests and `includeValues: false`.
- **Secret leakage:** keys and values can contain credentials. Default `valueMode: 'summary'`
  and key redaction; never log raw values to `console`.
- **Observer effect:** subscriptions enable the Rust drop log. Detach must restore the
  exact prior state; zero-cost tests enforce this.
- **Version skew:** protocol is numbered; unknown message kinds are ignored, not thrown.
- **Production safety:** panel is dev-only by default; explicit opt-in required.
- **Dependency order:** `devtools` depends on `@blaze-cache/core` dist declarations, so
  core must build first (already enforced by `pnpm -r` topological order in CI).
- **Index cost on writes:** secondary indexes add work to every insert/remove. They are off
  by default, gated by `bench:ci`, and reverted if the delta is not justified by data.
- **Async contract:** tiered mode's `getAsync()` is explicit and opt-in; `get()` never
  silently becomes async and is documented as memory-only.
- **Schema migration/skew:** v2 rows carry the new indexes; a newer schema still resets the
  namespace, and v1 rows migrate in place. Test downgrade and multi-tab `versionchange`.
- **Quota exhaustion:** treat `QuotaExceededError` as a contained failure with the existing
  memory-only fallback, never an unhandled rejection.
- **Scope valve:** devtools is never dropped. Only `beta.4` (tiered) may move to 0.5.x/0.7.0 —
  never into 0.6.0, which treats tiered as a fixed dependency.

# Blaze Cache — 0.5.0 Roadmap (Developer Tools)

**Date:** 2026-11-20
**Target release:** `0.5.0`
**Baseline:** `0.4.0` (depends on the `0.4.0-beta.3` stages in
[`0.4.0-roadmap.md`](0.4.0-roadmap.md))
**Scope:** new `@blaze-cache/devtools` packages, in-app UI, cross-tab monitoring,
browser test infrastructure, documentation

## Goals and non-goals

**Goals**

- See every cache instance in the app: size, capacity, hit rate, TTLs, tags, persistence
  state, and a live event feed — without instrumenting application code.
- Perform actions from the panel: inspect, set, delete, clear, invalidate by tag, prune,
  touch/TTL, flush, hydrate, rotate generation, reset stats.
- Understand behavior across tabs: which tab wrote a key, stale/rca use of 0.4.0's HLC
  ordering, and what IndexedDB is doing.
- Keep the production hot path untouched when devtools is off.

**Non-goals (explicitly out of scope for 0.5.0)**

- A full Chrome/Firefox extension with a DevTools panel — the transport is designed for
  it, but the extension UI ships after 0.5.0.
- Time-travel debugging, replay, or snapshot persistence to disk.
- Changing cache semantics, eviction policy, or the by-reference value contract.

## Extension points in the current codebase

The devtools core attaches to surfaces that already exist; no core API redesign is needed:

| Need               | Existing surface                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Instance discovery | Explicit `attach(cache)` (no global registry exists — `types.ts:69–72` already anticipates devtools)                                                   |
| Live mutations     | Wildcard `on(listener)` + 10 `CacheEventType` values (`types.ts:104–114`, `events.ts:58–284`)                                                          |
| Evict/expire       | Drop log via wildcard subscription → `CacheEventBus.wantsDrops` / `#syncDropTracking` (`cache.ts:214, 1560–1566`)                                      |
| Metrics            | `stats(): CacheStats` with `hits, misses, evictions, expirations, invalidations, size, capacity, hitRate` (`cache.ts:474–478`, `types.ts:46–56`)       |
| Contents           | `keys()`, `entries()`, `entry(key)`, `ttl(key)`, `tagsOf(key)`, `keysWithTag(tag)` (`cache.ts:426–456`)                                                |
| Persistence        | `persistence.stats()` — 15 fields incl. `pending, flushes, recordsWritten, errors, lastFlushAt` (`persistence/types.ts:135–166`, `cache.ts:1423–1440`) |
| Cross-tab          | 0.4.0 BroadcastChannel sync with `clientId` + HLC ordering (`0.4.0-roadmap.md`, Stage 3)                                                               |
| Zero-cost gate     | `CacheEventBus.hears/size/wantsDrops` (`events.ts:63–99`) — no listeners means no drop log and no snapshot work                                        |

**Critical constraint:** `entry()`/`entries()` return **live by-reference values**
(`cache.ts:131–143`). Devtools must never hand those to the UI directly: snapshot through
a safe summarizer (`structuredClone` in try/catch, size/depth caps, fall back to a type
label), and redact keys matching secret patterns (the identity-key collision fix in
`d175f6a` is a reminder that cache keys can carry credentials).

## Stage 1 (0.5.0-beta.1) — Observability core

Create `@blaze-cache/devtools` following existing package conventions (plain `tsc`,
`src/*.ts` + `index.ts` barrel, `test/*.test.mjs` with `node:test`, package README with
the standard logo header).

1. **Registry & lifecycle:** `attach(cache, { label? }) -> handle`, `detach`, `list`,
   `dispose`. Attach registers wildcard event listeners and keeps a weak reference to
   the instance; `dispose()` removes all listeners so the drop log switches back off.
2. **Versioned protocol:** `{ protocol: 1, tabId, clientId, cacheId, ts, kind: 'snapshot' | 'event' | 'action', payload }`.
   Types exported from `src/protocol.ts` so future transport implementations share them.
3. **Snapshot builder:** on demand (never on the hot path) — `stats()`, `size()`,
   `capacity()`, `keys()`, summarized `entries()`, per-key `ttl`/`tags`,
   `persistence.stats()`. Cap entries and payload bytes (`maxEntries`, `maxValueBytes`)
   with explicit truncation markers.
4. **Safe summarizer:** clone-or-describe values; handle `BigInt`, `Map`, `Set`,
   `ArrayBuffer`, `Uint8Array`, cyclical objects, functions, and non-cloneable externrefs;
   never throw into the host app.
5. **Event feed:** ring buffer (default 500) of the 10 event types, with key, timestamp,
   and tab/client attribution; `onEvent` subscription for UI consumers.
6. **Redaction:** default-on `redactKeys` patterns (e.g. `authorization`, `token`,
   `cookie`) and a `valueMode: 'summary' | 'none' | 'full'` option; `'full'` requires an
   explicit opt-in.
7. **Zero-cost guarantee:** when no consumer is attached, no listeners, no snapshots, no
   timers. Verify with allocation/event-count tests.

**Wire-up:** add `"@blaze-cache/devtools"` to `tsconfig.base.json:24–33` path aliases;
`pnpm -r test` / `typecheck` pick up the package automatically once it defines those
scripts (`js.yml:33–89`).

**Acceptance criteria:** `0.5.0-beta.1` published; unit tests for registry, protocol,
summarizer (including hostile/cyclic values) and zero-cost gate; existing core tests
unchanged and passing.

## Stage 2 (0.5.0-beta.2) — Actions and in-app panel

Create `@blaze-cache/devtools-react`: a React panel component plus a headless hook,
using only `workspace:*` dependencies.

1. **Headless hook:** `useDevtools()` → `{ caches, selected, snapshot, events, actions, attach, detach }`.
   Panel UI is optional — apps can build their own UI on the hook.
2. **Panel UI:** cache selector; overview cards (hits/misses/hit rate, size/capacity,
   evictions/expirations, pending flushes/errors); live event feed with filters; entry
   table with key, size, TTL countdown, tags, and a value inspector; persistence tab.
3. **Actions:** `get`/`peek`, `set` (JSON or text value, TTL, tags), `delete`, `clear`,
   `invalidateTags`, `prune`, `touch`, `flush`, `hydrate`, `rotate`, `resetStats`.
   Every action is attributed to a tab and reuses the same internal path as local
   mutations so 0.4.0 multi-tab sync broadcasts them.
4. **Safety:** confirmation for destructive actions (`clear`, `rotate`, `prune`);
   disable the panel automatically when `import.meta.env.PROD` unless
   `devtools: { enabled: true }` is explicitly set; keyboard shortcut to toggle.
5. **Examples:** wire the panel into all 7 Vite examples behind a dev-only flag; add a
   `dev:devtools` root script for a dedicated demo app.
6. **Docs:** package READMEs, root README section, and a "Devtools" guide with screenshots.

**Acceptance criteria:** `0.5.0-beta.2` published; each action exercised in at least one
example and covered by an integration test; package READMEs complete.

## Stage 3 (0.5.0-beta.3) — Cross-tab, hardening, browser tests

1. **Cross-tab aggregation:** relay `snapshot`/`event` messages over a dedicated
   BroadcastChannel per namespace; show a tab list with per-tab cache snapshots;
   attribute mutations via `clientId`; address actions to a specific tab (or broadcast).
   Respect 0.4.0's HLC ordering — devtools must not itself create stale writes.
2. **Transport abstraction:** `DevtoolsTransport` interface with an in-page default and
   a `PostMessageTransport` stub ready for a future browser extension. Protocol is
   versioned so mismatched builds degrade instead of crashing.
3. **Performance hardening:** throttle snapshots and event feed (e.g. 4 Hz, coalesced),
   virtualize the entry table, offload summarization to idle callbacks, and add a
   `maxTabs`/`maxEvents` cap. Re-run 0.4.0's benchmark suite with devtools attached vs
   detached; publish the overhead number honestly.
4. **Privacy/security:** default redaction reviewed; no network calls; CSP-friendly
   (no `eval`, no inline scripts); dependency audit (`cargo audit`, `pnpm audit`); extend
   `docs/security/` with a short devtools threat note (what the panel can see, what it
   redacts, how to disable in production).
5. **Browser test infrastructure:** add `benchmarks/browser/` and/or `tests/browser/`
   with Vite + Playwright (0.4.0 Stage 1 already proposes this workspace). Cover panel
   render, each action, two-tab propagation, and production auto-disable. Add a CI job
   in `js.yml` running Playwright with pinned browser versions.

**Acceptance criteria:** `0.5.0-beta.3` published; Playwright suite green in
Chromium/Firefox/WebKit; no redaction bypass found; overhead number published; docs
complete. **Feature freeze.**

## Risks and guardrails

- **Live-value aliasing:** devtools must not mutate cache contents via returned references —
  snapshot first, always. Covered by summarizer tests.
- **Secret leakage:** keys and values can contain credentials. Default `valueMode: 'summary'`
  and key redaction; never log raw values to `console`.
- **Observer effect:** subscriptions enable the Rust drop log. Detach must restore the
  exact prior state; zero-cost tests enforce this.
- **Version skew:** protocol is numbered; unknown message kinds are ignored, not thrown.
- **Production safety:** panel is dev-only by default; explicit opt-in required.
- **Dependency order:** `devtools` depends on `@blaze-cache/core` dist declarations, so
  core must build first (already enforced by `pnpm -r` topological order in CI).
